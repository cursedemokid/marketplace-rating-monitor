# wb-rating-monitor

Ежедневный мониторинг рейтингов и отзывов Wildberries: система собирает
показатели товаров, находит негативную динамику, объясняет её причины через
AI и сама пишет сотруднику, что и где пошло не так.

**Статус:** код ежедневной цепочки, двух кабинетов, ролей, номенклатуры,
отчётов и ограниченного AI подготовлен к передаче DevOps. Книги и графики
приняты заказчиком 16.10.2026; десять отзывов после тайм-аута разобраны.
Черновик на 474 товара импортирован без заполнения пустых полей. 15.10
успешно собран снимок за 14.10: 470 товаров `default`, 4 `DemoSeller`, сохранено
30 713 отзывов и перепроверено 14 прошлых снимков. 20.10 дозагружен период
29.09–19.10: всего 9 954 снимка и 23 563 дополнительных отзыва. `history`
на 19.10 подтверждает полную 16-дневную серию у 470/470 товаров `default`
и 4/4 `DemoSeller`; пропусков дат и расхождений счётчиков нет.

20.10 добавлено сравнение выбранных N дней с предыдущими N днями: количества,
процентные изменения, доли, разница в п.п., рейтинг и семидневный выкуп.
Все колонки доступны в общей таблице; карточка содержит дневные графики и
таблицы значений. Первая XLSX-книга использует те же расчёты и содержит
пять нативных графиков. Формулы, покрытие ТЗ и воспроизводимые измерения —
в [матрице соответствия](docs/10_СООТВЕТСТВИЕ_ТЗ.md).

16.10 заказчик подтвердил новую независимую сотню: 93 строки без изменений,
7 исправлены. Эталон хранится отдельно от предсказаний AI. Micro-F1 = 0,825939
при пороге 0,75; отдельная свежая серия дала 100 успешных первых попыток из
100 при пороге 95. Результаты, версия промпта и параметры зафиксированы в
[протоколе AI-приёмки](docs/ai-acceptance-DemoPhone.json).
`ai.automatic_enabled: true`; лимит проекта — $100 за календарный месяц
по Москве. Справочник содержит 34 причины. В таблицах отчёта видны все
34 строки, включая справочные «причина не указана» и «работа ПВЗ»:
они выделены голубым и не входят в «Общий итог». Внешние причины также
не входят в графики частых товарных проблем и AI-резюме сигналов.

После приёмки обработана оставшаяся очередь: 27 текстовых отзывов через AI
и 19 пустых локально. Повтор запуска не создал платных запросов.
10 отзывов из предыдущей неудачной серии разобраны агентом по согласованным
правилам: первоначально сохранены 14 связей с причинами, повторных платных
запросов нет. После отклонения дополнительной причины осталось 13 связей.
Исходная заявка с тайм-аутом и её полный резерв сохранены; прежний результат
серии остаётся 90/100. По решению заказчика кандидат «платный возврат»
отклонён; открытых согласований по этой причине нет.
На 16.10 обычная очередь и очередь закреплённых отзывов без меток были пусты.
Новые сборы пополняют очередь; актуальное состояние видно во вкладке «AI и модерация».
HTTP timeout увеличен до 180 секунд.
Книги с полным сравнением периодов —
`outputs/spec_closure_2026-10-20/ratings.xlsx` и
`outputs/spec_closure_2026-10-20/reasons.xlsx` (13–19.10, со справочными строками).
При проверке 16.10 месячный расход с резервом составлял $0,116971 из $100.

20.10 заказчик разрешил расход запроса №75 сверх первоначальной оценки.
Учёт сверен с завершённой записью A6API: 30 146 входных и 999 выходных
токенов, 158 единиц квоты / 500 000 = $0,000316. Защитная блокировка этого
запроса снята; исходная запись и сверка сохранены в
`outputs/reviews_2026-10-20/reconciliation*.json`. Для классификации и её
предварительного плана резервируется полный `ai.max_input_tokens`
(32 768), даже если оценка отправляемого текста меньше. Пакет, не помещающийся
в этот предел, отклоняется до оплаты. Расход выше входного или выходного
предела по-прежнему блокирует платные запросы; месячный лимит остаётся $100.

Рабочая доставка в групповой чат Телемоста разрешена (`notify.dry_run: false`).
Тестовая доставка прошла без дубля при повторе. Книги проверены программным
открытием и рендером и приняты заказчиком после исправления дат и графиков.
Текущая модерация и дальнейшая эксплуатация —
[docs/06_ПЛАН_ОСТАВШЕЙСЯ_РАБОТЫ.md](docs/06_ПЛАН_ОСТАВШЕЙСЯ_РАБОТЫ.md),
приёмка и передача — [docs/08_ПРИЁМКА_И_ПЕРЕДАЧА.md](docs/08_ПРИЁМКА_И_ПЕРЕДАЧА.md).
Проект опубликован в GitLab. Развёртывание на Linux выполняет DevOps после
локальной приёмки; оно не входит в критерии приёмки проекта.

## Быстрый старт

```bash
uv sync                       # зависимости и .venv
cp .env.example .env          # подставить значения
docker compose up -d          # Postgres и Redis
uv run python -m app.migrate  # схема базы
uv run python -m app check    # прочитать конфиг
uv run pytest                 # тесты
```

В VS Code: открыть папку, согласиться на рекомендованные расширения,
выбрать интерпретатор `.venv/bin/python`. Конфигурации запуска и отладки —
в `.vscode/launch.json`.

## Три вещи, которые надо знать до старта

**1. Сигналы идут в чат Телемоста для бизнеса.** Администратор Яндекс 360
создаёт бота в разделе «Телемост → Боты» и добавляет его в чат.
Текущий адаптер использует Bot API Яндекс 360. Порядок подключения —
[в разделе 2 инструкции по доступам](docs/03_КЛЮЧИ_И_ДОСТУПЫ.md).

**2. Для сигналов нужна своя история снимков.** Сравнение «неделя к неделе»
требует собственных последовательных снимков в PostgreSQL. Проверка
14-дневной базы доступна через `./dev history`; порядок запуска описан в
[регламенте развёртывания](docs/07_РАЗВЁРТЫВАНИЕ_И_ИСТОРИЯ.md).

**3. Восемь из пятнадцати фильтров Wildberries не знает.** Пачка, Линейка,
Тип, Вложимость, Категория, Бренд-2, Комплект, Количество в комплекте —
внутренний справочник. Импортирован черновик на 474 товара. Неуказанные
значения, в том числе «Бренд-2», оставлены пустыми.

### Браузерные E2E-тесты

```bash
uv sync --group e2e
uv run --group e2e python -m playwright install chromium
./dev e2e
./dev e2e --backend     # backend-тесты на отдельной временной БД
./dev e2e -k catalog    # только сценарии каталога
./dev e2e --headed     # показать браузер при наличии графической сессии
```

Нужен локальный PostgreSQL и пользователь с правом `CREATEDB`. Раннер берёт
параметры подключения из `.env` (`DATABASE_URL`); для отдельного тестового
PostgreSQL можно задать `WB_E2E_ADMIN_DATABASE_URL`. Он создаёт уникальную БД
`wb_e2e_<uuid>`, применяет миграции, загружает искусственные данные и запускает
отдельную копию API на свободном порту `127.0.0.1`. После проверки API
останавливается и удаляется только созданная этим запуском база.

Тесты в `e2e/` проверяют вход, роли, вкладки и легенды, названия и фильтры товаров,
добавление в наблюдение, пороги, номенклатуру, карточку с графиками и скачивание
обеих XLSX-книг. Рабочая база не используется для тестовых записей; WB, AI и чат
не вызываются. Обычный `./dev test` запускает backend-тесты отдельно от браузера.

Результаты: `outputs/e2e/<run-id>/` — журнал сервера, JUnit и `result.json`
с результатом очистки; при падении сохраняются снимок экрана и Playwright trace.
Открыть трассу: `uv run --group e2e python -m playwright show-trace ПУТЬ/trace.zip`.
Эти файлы могут содержать тестовые пароли и токены; каталог `outputs/` не входит
в Git. При аварийном завершении всей ОС или `SIGKILL` проверьте имя оставшейся
БД в `result.json`; не удаляйте базы по общей маске.

### Проверка производительности

```bash
./dev performance               # полный стенд, включая сбор со штатными лимитами
./dev performance --web-only    # отдельный повтор SQL/API и браузерных замеров
```

Нужны зависимости группы `e2e`, Chromium и локальный PostgreSQL с `CREATEDB`.
Стенд создаёт свою временную БД: 1000 товаров двух кабинетов, 181 день снимков,
500 000 сохранённых отзывов и 30 000 новых через имитацию WB с задержкой 200 мс.
Лимитеры настоящие, поэтому полный прогон занимает десятки минут. Внешние
сервисы, оплачиваемый AI и чат не используются. API и браузер проверяются за
90 дней, с 30 последовательными замерами и пятью параллельными пользователями.
Артефакты и результат удаления БД находятся в `outputs/performance/<run-id>/`.

Для отдельно разрешённого замера реального WB сначала создать копию
`./dev backup`, затем выполнить:

```bash
uv run python scripts/benchmark_live_collect.py --backup backups/ИМЯ.dump
```

Команда собирает только вчерашний день текущих кабинетов с перепроверкой
истории и сохраняет `outputs/performance_live/<run-id>/result.json`.
Она обновляет рабочие снимки, но не вызывает AI и уведомления. Реальный замер
содержит фактическое число товаров; результат стенда не является доказательством
проверки 1000 реальных товаров WB.

AI-приёмка требует micro-F1 не ниже 0,75 по утверждённой человеком разметке
и минимум 95 успешных первых попыток в отдельной свежей серии из 100.
Оба порога пройдены 16.10.2026. После смены модели, промпта или размера пакета
автоматический AI отключают до новой проверки.

В отчёте причин доля каждой строки считается от всех негативных отзывов дня
по выбранным артикулам. Один отзыв может входить в несколько строк; «Общий
итог» считает уникальные отзывы с выявленной подтверждённой товарной причиной.
Внешние жалобы на работу ПВЗ исключены из причин и итога; знаменатель не меняется.
Если негатива за день нет, процент остаётся пустым.
Цвета строк причин закреплены за значениями: 0% — зелёный, 50% — жёлтый,
100% — красный. Итог определения причин остаётся нейтральным.
Лист «Графики» содержит частые причины за период, динамику их долей,
количество отзывов по причинам и общий объём негатива. Доли за период
рассчитываются от общего количества негативных отзывов, не усреднением
дневных процентов. Формат дат в обеих книгах закрепляет точки как
буквальные разделители (`07.10.2026`).

После `migrate` создайте первую учётку через `add-user`; дальнейших
пользователей администратор может добавить через `POST /api/users`. Вход —
`POST /api/login` с JSON `username` и `REDACTED`; возвращённый токен
передаётся заголовком `Authorization: Bearer ...`. Доступны `GET /api/me`,
`POST /api/logout`, `GET /api/reports/ratings` и `/api/reports/reasons` с
параметрами `start`, `end`, повторяемым `nm_id`, а также
`GET /api/signal-settings` и `PATCH /api/signal-settings/{signal_type}`.
Менять пороги может только администратор; история изменений пишется в БД.
Для сбора карточек и отзывов нужны категории «Контент» и «Вопросы и отзывы».
Без категории «Аналитика» сбор сохраняет доступные данные, но снимки
рейтинга и выкупа помечаются неполными, а анализ и уведомления не запускаются.
Сбор читает и карточки из корзины WB: отзывы по ним сохраняются, но сами
удалённые товары не входят в текущий мониторинг. В запросе воронки явно
указан `limit` по размеру пачки; без него WB возвращает не более 50 строк.
Токен может иметь права записи: приложение использует
его только для получения данных. Команды `check` и `collect` локально
проверяют категории по JWT, а клиент WB разрешает только перечисленные
методы получения данных. Действительность токена и подпись проверяет WB API.
API слушает только loopback по умолчанию. Перед доступом с других машин
потребуется HTTPS на обратном
прокси и ограничение частоты запросов входа.

После `./dev api` откройте `http://127.0.0.1:8080/`. Первый экран показывает
последний неподавленный сигнал каждого артикула за выбранный период;
доступны таблица артикулов, карточка с графиками, история, две выгрузки и
пороги. Токен входа хранится только в памяти вкладки, поэтому после
перезагрузки потребуется войти снова. Фильтры периода, карточки WB и
внутреннего справочника общие для таблицы, сигналов и выгрузок. Значения
внутреннего справочника импортированы; администратор может сверить новый
XLSX и править отдельный товар.

В GitLab CI файл `.gitlab-ci.yml` поднимает PostgreSQL, применяет миграции и
запускает Ruff, mypy и все тесты, включая интеграционные. На реальном GitLab
этот pipeline ещё требуется запустить.

Для PostgreSQL из `docker-compose.yml` команда `./dev backup` делает архив в
формате `pg_dump -Fc`; `./dev verify-backup ПУТЬ` восстанавливает его во
временную базу, проверяет таблицу товаров и удаляет временную базу. Каталог
`backups/` и архивы доступны только владельцу и исключены из Git. На сервере
нужно назначить ежедневный запуск, хранение копий вне сервера и срок хранения;
локальная проверка восстановления сама по себе не заменяет этот регламент.

Контейнер проверяет `python -m app health`: после `collector.run_at` плюс
`health_grace_hours` нужны успешный прогон и снимок за вчера. Docker
помечает контейнер `unhealthy` при пропуске; на сервере ещё требуется
подключить оповещение к этому статусу.

Если ежедневный сбор завершился частично, анализ и отправка новых сигналов
останавливаются. После исправления причины повторите `./dev catch-up`:
он продолжит с незавершённого этапа соответствующей даты.

`make` намеренно не используется: в системе его может не быть, bash есть
всегда.
